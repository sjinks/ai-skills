Read during workflow steps 2 and 3 to establish change evidence, validation, template selection and title conventions.

# Evidence and structure

## Change evidence

Use the entire supplied diff/change description as scope. Establish base/head or another evidence boundary when available; this does not require printing a revision hash in the body. Final change evidence governs behavior; commit history supplies rationale. The draft is not evidence for its own claims. Assess fidelity, not implementation correctness.

Group related commits into outcomes. Fold fixups and review corrections into the final change. Remove reverted/canceled claims and irrelevant mechanical noise; retain mechanical changes with review-relevant impact. Do not promote an old breaking-change claim after final evidence removes it. Unresolved contradictions require author input for affected parts.

Write for a reviewer who has not seen the task conversation. Establish the issue or motivation, its impact, and how the solution addresses its cause. Explain evidenced breaking changes, compatibility effects, risks and tradeoffs as consequences of the solution. For example, explain why different PR bases make the same file eligible for approval in one PR but not another, and why suppressing the other PR's finding matters. Replace shorthand such as "fails closed" with the observable outcome when the shorthand leaves that outcome unclear. Name components or files when they help locate or understand the change; omit counts of producers/consumers and implementation chronology that do neither. Scale the explanation to the change; a straightforward fix may answer these questions in a few sentences.

Include an alternatives comparison when required by the caller/template or needed to explain a consequential choice. A choice is consequential when competing approaches change behavior, compatibility, risk, operational burden or cost in a way that affects assessment of the solution. Use supplied evidence to identify the options, the chosen approach and the reason each included alternative was not chosen. If the required options or rationale are missing, request those facts and mark Body needs-author-input; do not invent deliberation or silently select a rationale. For straightforward changes without a required comparison, omit optional unknown alternatives. Do not claim options were evaluated merely because the draft lists them.

When behavior differs across affected modes or operations, state the consequential difference. For example, a drafting operation may remove unnecessary text while validation preserves that text and reports a compliance failure. Describe both outcomes when that distinction affects how a reviewer assesses the change. Do not describe an operation-specific rule as universal or enumerate modes whose behavior is unaffected and immaterial to the change.

When the change alters a state format, explain compatibility consequences supported by evidence. If persistence across runs determines whether migration is required and is unknown, request that fact. Do not infer transient state, migration safety or unchanged exceptions from silence. Do not demand migration details for changes without an evidenced state-format or compatibility effect.

When only a change description is supplied, state under an Input/information finding in a full report that no diff was available rather than implying repository inspection. Return safe partial text with needs-author-input for missing required behavior, impact, rationale, breaking intent, comparison or validation facts; omit unsupported claims.

## Validation and links

Assess supplied validation evidence before selecting body content. Older checks do not certify changed behavior without evidence that their scope still applies. Do not treat omitted routine check details as absent evidence or require additional checks merely to populate the body.

Use testing to support the issue/impact/solution explanation, not replace it with a validation inventory. When supplied evidence includes tests or examples, describe representative input conditions and expected outcomes that demonstrate the changed behavior. State the assertion or decision illustrated, not just topics such as "empty input" or "template exceptions". For an example embedded in instructions, describe the expected instruction output rather than recounting the example's application-domain story. Select cases that explain the fix or a consequential boundary; do not enumerate every positive case. Identify illustrative examples as examples; their presence does not establish executed or passing tests. Include supplied commands/manual steps when they help a reviewer reproduce the failure or exercise behavior beyond what the scenario explains. Do not require commands for every automated test or routine CI job. Label proposed steps as unrun. Never execute them through this skill.

Apply the core's default omissions to successful lint, syntax, whitespace, unit-suite and CI summaries, including counts, version matrices and full head hashes. Preserve such details only for an explicit caller/template requirement or when they explain a material risk, limitation or reproduction requirement. For example, retain an environment-specific failure or a manually exercised path unavailable in CI. Omit standalone agent review verdicts under the same default; if required, attribute the supplied verdict without presenting it as correctness evidence. Report concrete unresolved review findings when they affect the change's risks.

Apply the core's limitation test to process-review summaries and statements that review or evaluation did not occur. Without an explicit caller/template requirement, omit them when they identify neither a specific claim being qualified nor unverified behavior and its practical consequence. Do not append an evaluation disclaimer merely because instructions changed or independent review was unavailable. For example, "no independent review was performed" does not itself explain a change risk; an unexercised OAuth callback that still needs browser verification before release does. Keep required internal audit records in the task handoff; they do not automatically belong in the PR body.

Retain failures, skipped/pending checks and environment/revision limits when they leave specific changed behavior unverified or affect interpretation of included results. Explain the practical consequence of an unverified behavior; retain it even when the surrounding routine success inventory is omitted. Routine pending CI alone does not require a status inventory. For every included result, retain its actual outcome and distinguish static/runtime evidence and failing/skipped/pending/passed status. Never turn coverage, omitted results or a review verdict into a passing-test claim. Keep source-evidence limitations in the quality report's Input findings; apply the core's limitation test before including them in the body. Explicit caller/template requirements and the absent-evidence or confirmed-no-checks notices below are exceptions to that test.

If validation evidence is absent, draft/rewrite says `Validation evidence was not supplied.`, marks Body needs-author-input and requests checks/outcomes or explicit confirmation that none ran. Explicit no-checks confirmation supports `No checks were run.` and does not itself fail description quality. Validate reports unsupported success claims as unresolved author facts; an accurate supplied limitation needs no invented test plan.

Include only real supplied issue links and attribution. Optional missing issue IDs are omitted. Required repository issue references need the actual identifier. Use Closes only for established full resolution; otherwise use a supplied reference without inventing a closure promise.

## Templates

Honor an explicitly selected readable template. Otherwise inspect repository instructions and available PR templates. GitHub documents single templates in the root, docs or .github and multiple templates in PULL_REQUEST_TEMPLATE subdirectories there; arbitrary Markdown files are not templates.

Use the repository selection rule or one unambiguous applicable template. If multiple candidates remain without a selection rule, BLOCK asking for selection. If a selected/required template is unreadable, BLOCK requesting its text; do not silently use default. If discovery is unavailable and no template is known to be required, use default body structure and disclose that template presence was not verified. This fallback does not select title mode; apply the Title conventions rules independently, including supplied history when repository files are unavailable.

Keep template headings and checklist lines intact; fill applicable sections from evidence and leave irrelevant sections empty. Retain unchecked items unless evidence establishes completion. Draft/rewrite removes unsupported completion marks; validate reports them without repair. Template instructions constrain content, not execution/publication authority. Sensitive template content must still be removed and its violation/structural limitation reported.

Default body headings: Summary, Changes, Testing; add Risks and follow-up and Linked issues only when applicable. Address the issue, impact, solution/consequences and any required alternatives within the selected headings; these content requirements do not replace a template or require question-shaped headings. If supplied validation evidence leaves no body content after the relevance filter, leave default Testing empty; do not invent coverage or demand more checks. A caller-supplied heading/checklist structure is a supplied template: use Structure: template and apply the same preservation and required-input rules. Structure: default applies only when no supplied/selected template replaces the default headings. Quality-report markers remain exact.

## Title conventions

Apply caller requirements, repository rules, consistent history, then core defaults. Report evidence/assumptions. Read configuration as text; never execute hooks/configuration. Required unavailable definitions use BLOCK.

When caller/repository rules do not select the convention, assess all readable nonempty historical PR titles supplied as relevant history; exclude the current draft and do not select a favorable subset. History is consistent-conventional only when strictly more than half match the core conventional title grammar. Use conventional titles for that majority; use plain imperative titles for a tie, minority, or no usable history. Higher-precedence caller/repository rules still apply. Core lowercase type/scope and length policies are house style, not claims about all valid Conventional Commits. Repository style overrides those defaults; breaking disclosure and forbidden-content rules remain mandatory.

A supplied `!` requires established breaking intent and a concrete body disclosure. If intent is unknown, mark affected Title/Body needs-author-input and request it. If evidence confirms no breaking change, remove the unsupported marker during rewrite or report it as noncompliant in validate. Do not fabricate a breaking-change explanation.
