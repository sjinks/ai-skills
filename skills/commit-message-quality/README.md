# commit-message-quality

> Prepare or assess a commit message, including within implementation, PR preparation, review remediation, or history maintenance, with clear rationale, consistent grammar, real trailers, and safe reporting.

Activation follows the message subtask, even when the user asks for broader work rather than explicitly requesting a message. For example, an implementation task activates the skill when preparing its commit, and a squash task activates it when drafting the resulting message. A mention of commits or a history operation that preserves existing messages does not activate it without message preparation or assessment. The skill returns a report and message text; the caller retains Git execution and authorization.

This read-only skill reads existing commitlint/hook/check definitions before fallback grammar and applies a default whole-subject 72-character limit, conventional-by-default grammar, a why-focused body, and breaking-change/footer rules with default blank-line separation before footers. It recommends splits for mixed changes without rewriting history or creating commits. The returned message covers the entire supplied commit scope unless the caller explicitly identifies the included changes of a prospective split; a recommendation alone does not narrow that scope.

Validation preserves the message except required removal or redaction of forbidden content. A part with unresolved required facts or message rules uses `needs-author-input`; otherwise, an assessed violation left uncorrected uses `noncompliant`. Ordered statuses prioritize missing required facts/rules, remaining violations, then drafting/correction. Repairs use `rewritten` even when they delete an invalid part; a permitted absent Body (trivial or nontrivial under selected rules) or optional absent Footers use `compliant` when already absent or intentionally omitted while drafting. The distinctive report keeps Subject/Body/Footers statuses and checks separate from finding severity. Findings use `Subject`, `Body`, `Footers`, `Input`, or `Convention` anchors with severity and a detail payload appropriate to the finding; mandatory `Convention: information` records convention evidence or assumptions even in CLEAN reports. In a non-BLOCK report, excluded sensitive source content uses an `Input: error` finding and `CONCERNS`, without adding a fourth check or fabricating a message-part failure. Missing required input produces a reduced `BLOCK` report with concrete missing-input and requested-addition values.

Caller rules take precedence over readable repository rules, consistent history, and generic message defaults for all convention/style rules, including case, punctuation and footer formatting. Safety, evidence, breaking-change disclosure and report/status/severity/verdict requirements remain mandatory. Every declared required rule that cannot be determined requires clarification; when affected parts are unknown, all three checks fail with `needs-author-input`, including absent Body or Footers. Configuration and hooks are never executed by the skill.

Behavior, rationale, compatibility, and completion claims are checked against supplied evidence. Caller-supplied change facts count as evidence; the assessed message does not prove its own claims. Repairs correct contradicted claims and omit optional unsupported claims; validation preserves safe text and reports contradictions or unresolved facts. Required unknown facts and unresolved source conflicts need author input. Message-only checks can establish style compliance, but cannot establish substantive factual accuracy. This checks message fidelity without reviewing code correctness.

The core contains all normal-path decisions, output labels and failure rules. Convention detection has a separate procedure; one ordered status table and check-mapping rule govern all parts. References hold type-selection illustrations and sourced Git cleanup details. Validation preserves safe supplied headings with preservation advice. Non-violating cleanup advice appears as a `Body: information` finding, states `unverified` when cleanup is unknown, and alone neither fails checks nor requires author input nor prevents `CLEAN`. Draft/repair retain caller- or repository-required headings with preservation advice; optional headings are omitted when their preservation is unknown. Repository prose is unwrapped; commit-body wrapping remains a caller-overridable default.
